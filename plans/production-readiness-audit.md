# Аудит готовности к продакшену — TradeCollectorService

**Дата:** 2026-06-01  
**Аудитор:** Независимый автоматизированный аудит  
**Версия сервиса:** 2.0.0 / 1.0-SNAPSHOT (расхождение — см. пункт #18)  
**Вердикт:** ⚠️ **НЕ ГОТОВ К ПРОДАКШЕНУ** — 13 критических/высокоприоритетных проблем должны быть устранены до запуска

---

## Краткое резюме

TradeCollectorService — хорошо спроектированное Kotlin-приложение для сбора биржевых данных с криптовалютных бирж (Binance, Bybit) по WebSocket, обработки сделок через конвейер (пакетная вставка → фильтр объёмов → агрегация) и сохранения результатов в PostgreSQL. Кодовая база демонстрирует сильные инженерные принципы: чистое разделение ответственности, паттерн Circuit Breaker, корректное завершение работы и автоматизированный деплой.

Однако выявлено **13 критических/высокоприоритетных проблем** в области безопасности, целостности данных, ресурсного обеспечения, тестового покрытия и эксплуатационной готовности — любая из которых способна вызвать инцидент в продакшене.

## Проблемы по критичности

### 🔴 КРИТИЧЕСКИЕ (необходимо исправить до продакшена)

| # | Область | Проблема | Расположение |
|---|---------|----------|-------------|
| 1 | **Безопасность** | Эндпоинты мониторинга (`/health`, `/metrics`, `/status`, `/exchanges`, `/database/stats`) полностью открыты — без аутентификации, без ограничения частоты запросов. Раскрывают торговые данные, статистику БД и внутреннее состояние сервиса любому, кто может достучаться до порта 8080. | `MonitoringServer.kt:40-121` |
| 2 | **Целостность данных** | Таблица `filtered_trades` использует `PARTITION BY RANGE (timestamp)`, но **отсутствует автоматическое создание партиций**. Вставка записей с временной меткой без соответствующей партиции приведёт к ошибке PostgreSQL и **полной потере отфильтрованных сделок**. | `sql/001_init_schema.sql:81` |
| 3 | **Ресурсы** | Куча JVM настроена как `-Xmx512m` в `run.sh`. Для 5 инструментов × 1M записей окна × ~40 байт/BigDecimal = ~200MB только на скользящие окна. С учётом t-digest, очередей пакетов и пула соединений 512MB **недостаточно** — высок риск OOM/зависаний GC под продакшен-нагрузкой. | `scripts/run.sh:56` |
| 4 | **Целостность данных** | `DiskBuffer.saveBatch()` **не имеет ограничения размера** — при длительном отключении БД файл буфера на диске растёт неограниченно и может заполнить диск, обрушив сервис и потенциально повредив файловую систему. | `DiskBuffer.kt:19-33` |
| 5 | **Безопасность** | `.deploy.env` содержит захардкоженный IP VPS (`95.81.99.28`), учётные данные БД и пути к SSH-ключам. Даже если файл в `.gitignore`, его наличие на диске — риск утечки кредов. | `.deploy.env:1-24` |

| # | Область | Проблема | Расположение |

Смешивание блокирующей JVM-синхронизации с корутинами Kotlin может вызвать **истощение потоков** на `Dispatchers.Default`. | `BatchProcessor.kt:120-157` |

## Что УЖЕ готово к продакшену

Несмотря на перечисленные проблемы, следующие аспекты реализованы качественно:

1. **Архитектура** — Чистый конвейерный паттерн, хорошо определённые интерфейсы, качественное разделение ответственности.
2. **Корректное завершение** — `ShutdownChain` с пошаговыми таймаутами предотвращает зависание при остановке.
3. **Отказоустойчивость** — Circuit Breaker, DiskBuffer (персистентность неудавшихся записей), DeadLetterQueue.
4. **Переподключение** — Экспоненциальная задержка в ExchangeClient для WebSocket-реконнекта.
5. **Деплой** — Атомарный деплой через symlink с автоматическим откатом при провале health check.
6. **Схема БД** — Партиционирование, корректные индексы, семантика UPSERT, функции очистки.
7. **Пакетная обработка** — Настраиваемые размеры пакетов, конкурентная обработка по инструментам.
8. **CI/CD** — GitHub Actions: тесты при push, релиз при теге, автоматический деплой на VPS.

## Top-5 действий перед продакшеном

1. **Добавить автоматическое управление партициями** для `filtered_trades` (создавать партиции заранее или использовать pg_partman).
2. **Увеличить кучу JVM** минимум до `-Xmx2g -Xms1g` и добавить логирование GC (`-Xlog:gc*`).
3. **Добавить ограничение размера** `DiskBuffer` (например, 100MB максимум) с алертингом при достижении порога.
4. **Защитить эндпоинты мониторинга** — добавить простую токен-аутентификацию или привязаться к `127.0.0.1` с reverse proxy для аутентификации.
5. **Написать интеграционные тесты** — минимум: применение схемы БД, вставка/чтение сырых сделок, ответ health-эндпоинта.
